# Backend

## Runtime and repository

Use Java, Spring Boot, Spring Security and Spring Modulith in one deployable application, with PostgreSQL, Flyway and jOOQ. Use Spring MVC with blocking JDBC access. Start with one application instance. Add another instance only with an explicit plan for realtime fanout, job ownership and measured capacity. Object storage, SMS, content classification and push delivery are external adapters. Kafka, Redis, microservices and a custom policy engine are not scaffold prerequisites.

Use Gradle with its wrapper, version catalog, dependency locks and verification metadata. Pin a compatible stable Java/Spring/Modulith/jOOQ toolchain during bootstrap and record exact versions in build-owned files. Compatibility is established by a clean generation/build run, not by copying an old version list. [Gradle dependency locking](https://docs.gradle.org/current/userguide/dependency_locking.html)

The repository areas are backend for Java, apps for executable Flutter applications, packages for reusable Flutter packages, contracts for authored interfaces, content for authored quiz/profile catalogs and docs for these references. Create a directory when it contains a real artifact. Start with one Java application project; a separate code-generation task or small build component is justified when it removes the bootstrap dependency on application compilation.

## Business modules

Modules are top-level packages under fm.lemon. Their exposed interfaces are in explicitly named API packages; remaining types are internal. Do not create four mandatory sublayers in a module with one simple operation. Use application services for orchestration, domain types for substantial pure rules and persistence/adapters for implementation details as they become useful.

| Module | Owns | Allowed dependencies |
|---|---|---|
| identity | Accounts, sessions, phone lookup keys, account access, per-account mutation guards | None |
| safety | Doors, blocks, reports, review evidence, restrictions, moderation policy | identity |
| quiz | Quiz versions, attempts, completions, collections | identity |
| media | Uploads, object keys, variants, publication and deletion state | identity, safety |
| profile | Nicknames, city, bio, representation references, interests and prompt catalogs/answers | identity, safety, media, quiz |
| messaging | Pair state, refusals, cooldown timestamps, accepted-send usage, requests, conversations, messages and snapshots | identity, safety, profile, quiz |
| discovery | Feed selection, exposure and ranking; detailed state follows the discovery study | identity, profile, quiz, safety, messaging |
| notification | Device push registrations, preferences, delivery attempts | identity, messaging, safety |

Create all eight module packages during bootstrap, with package-info.java module metadata, named api package metadata and the allowed dependency directions above. These declarations establish the layout and exposed package boundaries. Add callable APIs, services, tables, events and adapters with the behavior that uses them; a declared module does not need a placeholder endpoint or an empty repository. Schemas arrive with their first owned migration. [Spring Modulith module declarations](https://docs.spring.io/spring-modulith/reference/fundamentals.html)

This is the first-release runtime map. Trait Signal, subscriptions and boosts remain planned in Product and Delivery. Their studies precede model-specific schemas, events and algorithms; Commerce ownership and dependencies are designed when paid capabilities are scheduled. Do not create a fake billing module or trait-vector storage merely to preserve the roadmap. Quiz-scoring and Discover studies also precede their production algorithm implementations.

Dependencies cover type references, synchronous calls and subscribed event types. The graph is acyclic. Notification can subscribe to Messaging and Safety; those modules do not call Notification. Safety does not subscribe to Messaging events while Messaging calls Safety. Trusted callers submit safety observations through a Safety-owned API; moderation decisions use Safety-owned events consumed by the owning business module. Report creation for a message first resolves participant access and a permitted evidence snapshot inside Messaging.

Exchange-origin protective HTTP commands are orchestrated by Messaging through Safety's API. Safety owns blocks, report registration, evidence, reason catalogs and their action identities; Messaging owns exchange authorization, refusal/pair transitions and private list/label preferences. Block-context HTTP reads compose a Safety page with currently authorized Messaging/Profile context through batch APIs. Safety does not call those modules back to assemble a consumer DTO. Report/operation receipts require only Safety's own authorized records. These routes add no reverse dependency or generic cross-module workflow engine.

Enforce allowed dependencies with Spring Modulith metadata and its standard ApplicationModules.verify(). Explicitly declare allowed dependencies and named API interfaces; an api package name alone does not configure the boundary. Verification checks cycles and access to module internals. Keep a few additional ArchUnit checks for generated persistence ownership and API type leakage. These checks are automated boundaries, not database privilege isolation. [Spring Modulith verification](https://docs.spring.io/spring-modulith/reference/verification.html)

Use the framework's standard explicitly-annotated module detection so technical packages do not accidentally become business modules. All eight business roots carry ApplicationModule metadata; allowed dependencies target their named api interfaces. Assert the complete discovered set, including modules without behavior. Unannotated business code, open modules or broad exclusions cannot be used to pass verification. [Standard detection strategy](https://docs.spring.io/spring-modulith/reference/fundamentals.html#customizing-module-detection)

## HTTP adapters and technical wiring

Keep consumer HTTP controllers and transport mapping under fm.lemon.http, with generated interfaces/models under fm.lemon.http.generated. Technical startup, security-chain and infrastructure wiring lives under fm.lemon.configuration; the application entry point is at fm.lemon. These are technical packages outside the eight business modules. [ADR 5](adr/0005-http-adapter-boundary.md) records the rationale and limits.

Controllers authenticate through the configured security boundary, validate transport input and delegate to the owning module's public API. They do not own business transactions, policy decisions, SQL or repositories. A generated interface spanning several owners can delegate each operation to its owner without creating a reverse module dependency. Messaging still orchestrates exchange-origin protection and block-context composition; Safety retains its records and policy. HTTP mapping uses already-authorized API projections, never a general account object with fields hidden afterwards.

Business modules cannot reference fm.lemon.http, generated HTTP types or application configuration. HTTP/configuration code can access business modules only through their named APIs and cannot access persistence. Shared technical wiring contains no business state or orchestration. ArchUnit checks these directions and the allowed first-party package roots, since unassigned technical code is outside Modulith's business graph. Do not grow a generic application-service layer in the HTTP package.

Profile can compose its own fields with Quiz's public collection API. Discovery composes candidate summaries through batch APIs. Identity returns account/session state and does not call Profile to assemble onboarding readiness. The mobile host reads profile readiness separately and routes into profile setup, preserving the dependency direction. API signatures expose purpose-specific API types, not jOOQ records, persistence entities or internal account objects. Technical configuration can be shared where needed, but business rules remain owned.

## Persistence and code generation

Use one database with one schema per implemented business module. Runtime-owned framework tables use a platform schema. One application database principal can access these schemas, so schema names express ownership; tests and review enforce cross-module access restrictions. A module reads another module's data through its API, including bulk reads.

Use jOOQ for visible, parameterized queries and explicit mapping. Do not add a second ORM or a generic repository hierarchy. Raw SQL is normal in migrations; runtime queries should ordinarily use generated owned-schema types. A required unusual SQL operation stays in its owner's persistence adapter and is reviewed directly.

Flyway migrations are append-only once applied to a shared environment. Use one ordered migration stream with clear schema ownership. Code generation applies those migrations to an isolated PostgreSQL database and produces schema-specific types before application compilation. It must not depend on testClasses or a running production application. [jOOQ Gradle code generation](https://www.jooq.org/doc/latest/manual/code-generation/codegen-execution/codegen-gradle/)

Database constraints back up stable invariants: collection uniqueness, one completion per attempt, one open exchange per unordered pair, message operation uniqueness and valid state references. Feature tests verify both expected conflicts and rollback. External API compatibility and database rollout are separate concerns; use additive schema changes, backfill and delayed removal when two server versions may overlap.

## Transactions and concurrent contact

This section implements the ownership and ordering needed by Domain's approved pair, context and return rules. A conversation awaiting a return reply retains the exclusive open-pair slot. Declined/ended exchange return rechecks that no newer open exchange has taken it.

The outer application operation owns a short Spring-managed transaction. Use one DataSource, its JDBC transaction manager and a Spring-integrated jOOQ DSLContext. Synchronous module calls, including guards, join its physical transaction; do not split that operation with independent connections or REQUIRES_NEW. Verify transaction entry through the Spring proxy or TransactionTemplate; a same-object call to an annotated method does not establish proxy-based interception. External provider calls happen outside database transactions. [Spring transaction propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html) [Transactional method boundaries](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

Identity exposes a server-internal mutation guard through its named api interface; this guard locks participating account rows in stable identifier order and requires an active transaction. Contact-affecting mutations use this protocol: request admission, replies, message sends, door changes, blocks, profile/anchor changes, quiz collection changes, account access changes and deletion. A two-account operation locks both before reading mutable policy facts. This deliberately serializes a member's relevant writes at first-release scale; measure contention before making locks more granular. Ordinary authentication and browsing reads do not acquire these write guards.

Use PostgreSQL READ COMMITTED for guarded operations. Acquire guards first, then read authoritative policy in subsequent statements so a writer that committed while the operation waited is observed. Do not reuse a preflight snapshot as authorization. Bound lock and statement waits within the request deadline; a failed transaction rolls back before reconciliation or retry with the same operation identity. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

For a registered first-message candidate, processing and admission proceed as follows:

1. Authenticate, validate input and reject known access failures before invoking a paid provider. Replay an already committed operation only while authorized. For pending checking work, classify the submitted text outside a database transaction; tie any nudge acknowledgement to the same account, text digest and policy revision. These preliminary reads cannot grant admission.
2. Begin the transaction and acquire participant guards in stable order.
3. Check the operation identity and exact live candidate/work generation again; require a still-applicable content assessment and explicit send authority after human review. Then re-read account access, profile readiness, quiz completion, door revision, restrictions, pair state and accepted-send allowance; resolve the selected anchor and snapshot.
4. Insert the request, pair state, quota usage, candidate SENT state/admission receipt and required durable local event publication atomically.
5. Commit, then run notification and other external side effects.

Door changes and blocks that commit before admission are therefore observed; changes after it cannot rewrite accepted identity. Unique constraints remain necessary even with locking. Use the same guarded state transition for reply-versus-decline and duplicate first replies. External classifier approval alone never authorizes a send.

Exchange actions use the shared mutation protocol in Contracts. Check an authorized committed key before treating a changed lifecycle as new work. For a new action, establish original-role and visible-phase permission before returning revision conflicts. Under the ordered guards, compare the observed lifecycle cycle and commit the action receipt, message, applicable refusal and pair transition together. Ordinary messages share a cycle revision; closing/reopening invalidates it. A delayed send or end from an earlier cycle cannot affect a reopened conversation.

Protective block/report commands have their own protocol in Contracts. Under the same ordered participant guards, a block commits the Safety restriction and owner/context receipt with Messaging's affected open-pair transitions and durable repair work. Acting from old history must also stop a newer open exchange for that pair. An asynchronous handler cannot be the first point at which message admission learns about a committed block. Keep internal account-level protection distinct from context-scoped public block records; neither IDs nor creation timestamps can merge otherwise-unlinked anonymous contexts.

Report registration commits Safety's allegation, authorized evidence and work with any required pending-request closure/refusal. Read current phase after the guards: if a reply won, register the report without ending the now-established conversation. Closing an already-closed request cannot add another refusal; another deliberate report may register a new allegation without altering that closure. Never apply an old report's closure to a newer pair exchange. Evidence resolution and retention cleanup must use compatible ordering so registration cannot copy withdrawn text from an earlier unguarded snapshot. Provider/staff processing follows commit and cannot turn a receipt into proof of completed review.

Private preferences are participant-owned Messaging records. Serialize conditional edits with current participant access, using a revision independent of shared lifecycle and peer preferences. Include the original receiver's label only in that caller's permitted projection. List queries apply the caller's hidden flag, and only the explicit HIDDEN view includes hidden rows. These writes emit no shared message-journal entry and cause no peer-visible revision, refusal, notification or pair change.

Shared authored content needs its own ordering: completion and anchor admission hold a shared row lock on each referenced publication/catalog state until commit; retirement or withdrawal updates that state under an exclusive lock. Acquire account guards before content locks, ordering multiple content locks by a stable resource key. Publication does not acquire account guards while holding its content lock; per-account cleanup follows after commit. This prevents a version withdrawal from committing between validation and completion while avoiding a global account-lock sweep.

Messaging owns accepted-send counts and atomic enforcement of the applicable plan and protective limits. Sample one database admission instant after acquiring participant guards; count the rolling 24-hour interval specified by Safety using server timestamps. Check the applicable caps and write usage with the admitted request in the same transaction. Content deletion or receiver refusal cannot reset window usage. Retry guidance is an estimate under current known policy, not permission to send later automatically. Safety supplies protective limits and restrictions without querying Messaging tables or knowing whether an account paid. The first-release plan policy supplies the free-plan cap directly; it requires no billing framework. Future paid entitlements must supply their cap separately and cannot raise a protective limit. There is no receiver pending-request capacity counter, reservation or admission threshold. Messaging can provide batch load facts required by an approved discovery design without turning those facts into a contact cap.

## Identity and sessions

SMS verification uses a provider adapter with number and network abuse limits. Normalize numbers before deriving a versioned HMAC lookup key. Do not log or persist plaintext numbers in ordinary application records. The SMS provider necessarily receives the number; its retention and processing terms belong in the real-data review. A phone hash is pseudonymous personal data, not proof of a person or irreversible anonymization. Keep key versions with lookup records. Because retained hashes cannot be re-keyed without a supplied number, key rotation needs an overlap and retirement plan covering the lifetime of retained enforcement keys; it cannot simply discard the previous key.

Consumer sessions use opaque cryptographically random bearer access and refresh credentials, with only credential hashes stored. Access credentials last at most 15 minutes and never beyond the rotating family's absolute 30-day expiry. Check session revocation and current account access on authenticated operations. Support device-session logout and logout everywhere. Use Spring Security's filter chain and authorization integration rather than an application-wide custom interceptor. [Spring Security architecture](https://docs.spring.io/spring-security/reference/servlet/architecture.html)

Refresh rotation is atomic and serial per family. Reuse of an already-consumed refresh credential revokes the family. The mobile app serializes refresh calls and does not blindly retry an uncertain refresh: a lost rotation response requires login again. This accepts occasional reauthentication to avoid a replay grace protocol. Device-scoped session metadata is not cryptographic device binding. [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

Session creation, rotation and revocation acquire the account mutation guard before locking family state and re-reading current authorization. A credential lookup can identify which account to guard but cannot authorize from that preliminary read. This orders logout-all against concurrent login/refresh without reversing the account-before-family lock order. Single-family logout can use a current or retained consumed refresh credential solely for revocation, so access-token expiry does not prevent it; unknown credentials receive the same empty success response. Logout-all revokes every family existing at its commit, including the caller's, while a later approved login can create a new one. Neither operation restores credentials or creates a replay-response cache. [Contracts](contracts.md) owns their exact HTTP and uncertain-response behavior.

Keep OTP failure responses and pre-verification account existence indistinguishable. Provider-side OTP verification plus local attempt limits is preferred to storing low-entropy codes with ordinary unkeyed hashes. A ban can be disclosed only after number ownership verification. Number changes, recycled-number access and recovery need the decision recorded in Delivery before live-account authentication is enabled; a working SMS test does not settle those cases.

Staff authenticate through a separate OIDC realm/audience with MFA, separate sessions and explicit reviewer roles. Public mobile credentials cannot authorize staff routes. Separate contracts and builds reduce accidental exposure, while server authorization remains mandatory. Audit evidence reads, exports and enforcement changes. [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

## Exchange history consistency

Messaging owns a bounded change journal for HTTP history repair, separate from immutable message creation order. Write admitted messages, permitted lifecycle changes and content removal markers with their corresponding journal changes in the same transaction. Serialize journal append through the exchange's write boundary, including safety/cleanup writes, so a cursor cannot advance past a lower-position transaction that has not committed. Keep message references rather than copied sensitive bodies in that journal; materialize currently permitted content when reading a historical change. Receiver-private decline/folder state has its own participant projection and never enters shared history progress. This is a feature-owned repair mechanism, not a general event-sourcing framework.

The initial history window, participant view and recovery boundary must come from one consistent authorized database read. Separate ordinary READ COMMITTED statements can observe different commits; use one statement snapshot or a short consistent read transaction for that combined result. Changes pages capture a definite scan boundary and cannot advance past unprocessed changes. Authorization and content projection must agree within each response. Cleanup follows D4 and returns the explicit cursor-reset outcome when retained changes can no longer repair the supplied boundary; deleting journal rows must not silently produce successful empty recovery. Verify these cases with real PostgreSQL during implementation.

## Events, media and operations

Use synchronous APIs for decisions required by the current action. Introduce Spring Modulith's JDBC publication registry with the first required durable side effect. Publish inside the business transaction, with registry persistence on the same DataSource and transaction manager. Own its schema through Flyway and disable automatic runtime schema creation. Register actual consumers; publishing an event with no transactional consumer is not a durable task queue. Retry scheduling, alerting and completed-publication cleanup are explicit operational tasks. [Spring Modulith events](https://docs.spring.io/spring-modulith/reference/events.html)

ApplicationModuleListener opens a new transaction by default. A listener performing local cleanup may finish that work there; a listener requiring an external provider records idempotent pending work in the owning module, such as Notification's delivery record. A small worker claims a bounded batch in a short transaction, calls the provider after releasing it, then records the outcome in another short transaction. Interrupted claims must become eligible for recovery. Use provider idempotency where supported; an unknown provider outcome can still cause repeated delivery and must not be called exactly-once. Reuse framework registry operations and feature-owned records rather than creating a generic workflow engine.

Keep event payloads to the identifiers and facts the consumer needs. Avoid copying message text, phone numbers or credentials into serialized publications. Pending event types must remain readable across deployment; a Java class rename can affect persisted work. Safety's retention rules also apply to event and delivery records.

Moderated candidates stay in their owning feature: Profile controls change versions and publication; Messaging controls first-message versions and admission. Safety owns the review assessment and minimum required case evidence. Its durable decision events identify the exact submission/version. Profile rechecks and publishes a still-current valid save; Messaging records that the sender can explicitly continue, without admitting the request from the listener. Use the same guarded transaction ordering for cancellation, replacement and publication/admission, rejecting obsolete decisions. General review notifications can use existing Safety/Messaging events without claiming the owning operation has committed. This uses feature-owned records and the existing publication registry, not a generic workflow engine.

First-message registration uses the participant guards to authorize current input/context and atomically store immutable content, operation digest and durable work. It does not reserve a pair or allowance. Authorize a known creation/action replay before current target, context and allowance checks; otherwise receiver decline or spent quota could change a replay into a new admission attempt. Actions bind their own identity to the candidate and consequential body. A replacement supersedes only the named owned live version, in the same registration commit. Worker results apply only to the exact live version and current assessment generation; late results after cancel/replacement cannot send. Human approval records READY_TO_SEND and disarms automatic admission until the author's explicit Send. A required new human assessment disarms it again. Provider failure and failed final predicates remain safe unsent outcomes, never deferred allowance scheduling.

Profile registration is a separate short transaction before external content checks. Under the account guard, check the operation digest, saved base revision and explicit replacement target; atomically register the immutable patch and required work, superseding the previous candidate only if registration succeeds. Authorize replay before returning its current projection. Durable processing survives a lost HTTP response or worker interruption. A confirmed provider failure ends this candidate as NOT_APPLIED; it does not reactivate a superseded edit or create a human review case. An interrupted worker with no recorded outcome remains recoverable work, not evidence of provider success.

Profile applies a valid candidate in another guarded transaction after checks. Re-read current access, candidate state, base revision, content assessment and Domain's publication predicates; commit all changed fields, the resulting revision and APPLIED together. A failed predicate records a safe terminal problem without partial profile writes. Acknowledgement, cancellation and decision handling use the same guard and exact candidate identity; duplicate/late decisions cannot reactivate terminal versions. Increment the candidate's stateVersion for each visible state, prompt or disclosure change. The owning read projection must observe a consistent state/version pair, including content withholding. Existing account-before-content lock ordering also applies to catalog and media availability checks.

Media uploads use expiring, owned upload grants. Uploaded objects stay private until validated, processed, metadata-stripped and approved. Profile accepts only a ready, owned media reference. Publication and deletion handlers are idempotent; an account deletion cannot be undone by a late upload callback.

Notification consumes committed events, rechecks relevant access, respects preference and sends generic lock-screen text without message content, sender identity or quiz details. Provider acceptance is not proof the user received or read a notification. Realtime delivers committed updates; HTTP repairs history as defined in Contracts.

Start with typed server configuration deployed with the application. Secrets live outside source. Validate required settings at startup; production cannot fall back to test SMS, allow-all moderation or fake sessions. Add remote configuration only for an actual operating requirement.

Expose restricted health/readiness, request/error metrics, database latency and background-work backlog. Logs contain identifiers safe for their access level and never message text, credentials, phone numbers or anonymous identity links. The rollout, backup and restore checks are in [Quality](quality.md). Architectural alternatives are recorded in [ADR 1](adr/0001-modular-backend.md) and [ADR 2](adr/0002-persistence.md).
