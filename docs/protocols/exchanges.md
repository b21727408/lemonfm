# Exchanges, history and protective actions

[Contracts](../contracts.md) owns shared HTTP conventions; [OpenAPI](../../contracts/http/public-v1.yaml) owns the wire shapes. This reference owns the following cross-operation behavior. Read only the sections needed for the feature.

## Exchange views and actions

The server selects the view from the authenticated participant and permitted lifecycle. Before a conversation starts, the original sender sees OUTGOING_REQUEST, including after silent decline. That shape has no private request state, lifecycle revision, folder or action list. The receiver sees INCOMING_REQUEST with their own state and folder. Anonymous incoming peers have no handle or profile fields; the conversation-scoped handle appears only after a reply starts the conversation. An anonymous peer cannot fall back to an open profile when a representation becomes unavailable.

List membership and ordering use only caller-visible facts. Silent decline cannot remove or reorder the sender's outgoing item, move it into archive, or change their history progress. Shared context contains permitted admission-time snapshots, without hidden collection links, trait data or redaction reasons. Later reads cannot resurrect withdrawn snapshot content. Current allowedActions are hints for the exchange lifecycle operations; they do not grant permission or enumerate the separate protective and private-preference operations below.

The reply, decline and conversation mutations in this section require an author-scoped action key and the observed expectedLifecycleRevision. Scope uniqueness to author and operation kind; bind the key to the exchange and normalized consequential input. Authorize current access, then resolve a known committed operation before checking changed lifecycle/contact predicates. A changed body or target conflicts. For a new action, establish original-role and visible-phase authorization before comparing revisions, so the error cannot reveal a receiver's hidden closure. Recheck under Backend's ordered account guards; atomically commit the action receipt with only that operation's required message, lifecycle, refusal and durable-work changes. A text send does not record a refusal; decline/end creates no message. Protective block/report and private-preference edits use their separate protocols below.

A lifecycle revision identifies the observed request/conversation cycle. Close, return and resume invalidate old actions; ordinary messages do not invalidate another ordinary send. A stale reply cannot become a return, and a stale send/end cannot affect a reopened cycle. Text actions use the existing conversation limits and narrow critical-safety processing in Safety, without a new quiz prerequisite or first-request allowance charge. They still check current contact restrictions. Decline/end require the acting participant's access; a peer losing access cannot prevent that participant from closing their exchange.

The two return commands have distinct purposes. return-reply starts the first conversation after the receiver's refusal; the original sender sees an ordinary reply without a refusal marker or private operation kind. return sends one offer after the receiver ended an established conversation, enters AWAITING_RETURN_REPLY and keeps the pair occupied. Only the original sender's explicit resume reply restores ACTIVE. Both paths preserve original roles, anonymity and refusal history, and recheck blocks/access and competing open exchanges. Domain owns these product rules.

HTTP 200 confirms this action's commit or authorized replay. Its receipt contains a message reference where applicable, never a cached message body, current-state promise or peer activity. Recovery lookup resolves only the caller's action-kind/key namespace within that exchange; knowing another participant's key cannot expose their decline or return-reply receipt. After an uncertain response, reconcile the original action and read the current exchange before another deliberate action. A missing lookup while work might be running is inconclusive.

The shared 24-hour response-replay window does not end action uniqueness. Retain the minimum action identity/digest needed to prevent reuse while the exchange can still accept that action; body/evidence retention is separate and governed by D4. After resource removal, its identifier cannot be recycled into another writable exchange. Neither expiry nor a failed lookup permits a blind resend with a new key.

## History and recovery

Message sequence is immutable creation order within an exchange. It cannot track a later withdrawal of an older message. Recovery therefore uses a separate opaque change cursor; cursors are scoped to participant, exchange and traversal, and convey no authorization.

| Response | What it establishes | Client use |
|---|---|---|
| INITIAL history | Recent bounded messages, current participant view and recoveryCursor from one consistent authorized read boundary | Replace the transcript and start recovery from this boundary |
| OLDER history | Current permitted content before nextCursor | Prepend/deduplicate older messages; never advance recovery or replace lifecycle |
| Changes page | Ordered permitted upserts/removals, recoveryCursor, hasMore and a fresh participant view | Apply the whole page before adopting progress; continue while hasMore |

A historical change returns the message's currently permitted projection, not old stored text. UNAVAILABLE removes a retained message's body; REMOVE_MESSAGE removes its local entry. Repair includes withdrawals of messages older than the loaded window. Update/remove already loaded IDs and add new admissions without inserting unrelated old messages merely because they changed. Pages may contain no visible changes and still require continuation. A private receiver decline/folder/read action never enters shared history or advances the sender's cursor; the receiver recovers their own state through the participant view. With no shared change to advance, the supplied recovery cursor is preserved.

Invalid or wrong-scope cursors receive 400. Only after exchange authorization, a cursor beyond the retained repair boundary receives 410 HISTORY_CURSOR_RESET_REQUIRED. Discard downloaded history and bootstrap again, preserving unsent drafts and operation identities. Do not interpret expired recovery as an empty successful history or a reason to resend. D4 must set the change-journal and removal-marker lifecycle before real data; no numeric retention period is selected here.

The client serializes authoritative history/view reads per exchange and rejects obsolete session or reset generations. Socket notifications schedule/coalesce HTTP recovery; they do not install message bodies or replace confirmed HTTP progress. This avoids an older in-flight page restoring text after a newer removal. After local actions, reconcile the current view and history rather than fabricating state from a historical receipt. Mobile owns the controller behavior; actual races remain implementation tests.

## Protective actions and private preferences

Block and report commands resolve the peer through an authorized retained exchange. They require the acting member's access, not quiz completion, ordinary contact permission or the peer's continued account access. An ended/severed conversation remains reportable while retained. They do not require a shared lifecycle revision: protection/reporting remains meaningful when ordinary conversation state changes. Each command still reauthorizes its exact target under the ordered participant guards.

A block confirms account-level protection in both directions. Safety owns that restriction and the caller's known-context record; Messaging commits affected pair/active-exchange transitions with it. The operation must also stop a newer open exchange when invoked from older retained history. It does not create a report, charge a refusal or delete delivered messages. Before conversation start, the sender's historical outgoing view remains free of private closure details. A lost response is recovered from the author's BLOCK operation namespace. Repeating an owned context does not create another context row or move it to the top of the list.

Block records must not become an identity-linking index. Public blockId and creation time identify the caller's known context, not an underlying account pair. Separate otherwise-unlinked anonymous contexts remain separate even if protection resolves to the same account internally. A block initiated only by the counterpart is absent from the caller's list; a later own action records only that own intent. Anonymous contexts never gain a profile link through replay, grouping, a current-profile fallback or retention cleanup. When source context is unavailable, show UNAVAILABLE without lifting protection. There is no unblock operation.

Report registration requires a selected reason from the displayed target-specific catalog and may include the member's own context. D5 must approve the actual reason taxonomy and translations; the schema's synthetic example is not a default category. A stale/withdrawn catalog produces REPORT_REASON_CHANGED, preserves the draft and requires a fresh deliberate submission. A missing configured catalog produces service unavailability. The chosen reason records an allegation and never determines an automatic penalty.

Messaging resolves minimum relevant server evidence after participant and parent/message authorization. The message endpoint requires a retained peer-authored message; supplied text cannot impersonate evidence. A retained message with withheld text can still support an allegation using currently permitted metadata and user context. Safety registers the immutable report, restricted snapshot and durable review work. It does not obtain general access to Messaging persistence. Report registration and any required closure commit together: pending at commit means close that request, with one refusal only when its receiver closes it. If reply won the race and a conversation exists, report registration does not end it; the client refreshes the current view. Reporting old history cannot close a newer exchange for the pair.

HTTP 201 confirms a registered report; replay returns 200 for that same allegation. REPORT and BLOCK have separate author-scoped key namespaces bound to their complete targets and consequential input. Known authorized replay precedes stale target/catalog checks. Recover using the original key after a lost response; an in-flight miss is inconclusive. The shared replay-window and durable-uniqueness rules apply. Reporter receipt reads are authorized independently of source-history retention and disclose no evidence, private closure, accused identity or review/enforcement state. Receipt lists are ordered by registration, not staff activity. Reporter outcomes and appeals remain D5 work. D4 separately governs report evidence, receipts and retained block associations; no new numerical retention promise is introduced.

Private preferences use an owner-specific expectedRevision and a current read after an uncertain PATCH. They need no creation receipt or shared lifecycle revision. Hidden rows appear through view=HIDDEN and are excluded from ordinary groups; restoring a row returns it to its current permitted group. Hiding affects only that member's list, preserves pair/contact state, does not mute the existing notification policy and is not reset by a peer's message. Only the original receiver of an established conversation may set/clear a private label. A label is never a system-handle change, verified identity, peer notification or evidence amendment. Its value appears only in that receiver's own conversation view; it cannot enter the shared journal or advance peer-visible progress. Label omission in PATCH preserves it; null clears it. Invalid role/field or revision means no partial edit.
