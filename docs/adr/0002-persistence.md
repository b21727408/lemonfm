# ADR 2: PostgreSQL, jOOQ and owned schemas

Status: Accepted

## Context

Lemon.fm needs transactional request admission, pair uniqueness, ordered conversation history, collections and bounded discovery reads. Query behavior must remain visible during review, including when code is generated by an assistant. Schema changes also need a reproducible path from an empty developer environment.

## Decision

Use PostgreSQL as the authoritative store, Flyway for ordered migrations and jOOQ for generated typed SQL access. Each implemented business module owns its schema. Runtime framework tables use a platform schema. The initial application uses one database principal, with cross-module reads composed through owning APIs.

Generate types from migrations applied to an isolated PostgreSQL instance before application compilation. Code generation cannot require already-compiled application or test code that refers to those generated types. Keep generated Java sources as build outputs.

Use database constraints for stable uniqueness and integrity, with transaction tests for behavior that spans several records. The detailed mapping and concurrency protocol are in [Backend](../backend.md).

## Alternatives

JPA could handle simple record persistence with less explicit mapping. It is a valid technology, but this product's inbox, feed and concurrency work benefits from direct control of SQL and explicit fetching. Avoiding lazy-loading behavior is useful for this project's review workflow; it is not a claim that ORM-based projects are inherently poor quality.

Plain JDBC would avoid jOOQ generation, but require more manual SQL/result mapping and provide less compile-time feedback for schema changes. We accept a bounded generator workflow to reduce that repetition.

A database or build project per module would strengthen isolation, but complicate the transactions and setup needed for the first release. A single undifferentiated schema would reduce naming structure but make ownership easier to blur.

## Consequences

There is a code-generation dependency and some explicit mapping code to maintain. Generator and database versions must be compatible and pinned. Migrations require review for both data correctness and runtime rollout; generated compilation alone cannot validate them.

Schemas make ownership visible but are not a security boundary when one principal can access all of them. ArchUnit catches references to another module's generated types; SQL and API composition still need review. Do not promise that every boundary violation is impossible to type.

Discovery initially uses bounded batch APIs rather than cross-schema queries or an event-fed projection. Reconsider that read design using measured latency and database load. Reconsider separate credentials or stores only for a concrete isolation or deployment requirement.
